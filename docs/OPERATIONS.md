# Operations


## Credentials
- Never put a password in a file or in chat.
- **Credential resolution (product path).** Each secret comes only from what the setup wizard stored: the camera account of that camera (`camera:<device_id or id>` as `{"user","password"}`), and the TP-Link password of the saved account email (`cloud:<email lowercased>`). Nothing else is read. A camera without its own camera account has no fallback: Live shows "Add this camera's camera account in Settings to use Live view" and nothing is tried. A missing TP-Link account makes Verify refuse before any attempt, uncounted ("Save your TP-Link account first"). A store that cannot be read (denied prompt, locked keyring) refuses the same way and is never read as "no secret".
- **Developer fallbacks: `KINORA_DEV_SECRETS=1`.** Off by default. Only with this variable set to `1` in the environment of the server (or of `python -m kinora.creds`) are these used: the environment `TAPO_PASS` (user `rtspadmin`, override `TAPO_USER`), `TAPO_CLOUD_PASS`, the `.env` file in the data folder, the macOS `security` CLI, and the global keyring items (service `kinora`, account = camera user; service `kinora-cloud`, account = the saved TP-Link email). The cloud item is looked up only for the saved account email, never without an account. A secret that comes from them is shown as `dev_override`, and the server logs one line at startup: `developer credential fallbacks are ON`.
- **Existing developer setups:** if you kept your passwords in the environment or in the old Keychain items, add `KINORA_DEV_SECRETS=1` to the environment that starts the server to keep using them. The cloud item is found only when the saved account email (Settings) is the same as its Keychain account. Without the switch those items are ignored, and the cameras show as missing until you save them in the wizard.
- Store a global developer password without echo or argv: `python -m kinora.creds set` (and `TAPO_CLOUD_ACCOUNT=<email> python -m kinora.creds set --cloud`). Check which sources exist without printing values: `python -m kinora.creds status` (the legacy sources are listed only with `KINORA_DEV_SECRETS=1`).
- **Camera account per camera (Live view only).** Each camera may have its own camera account (user name and password created for that camera in the Tapo app). It is optional: Verify, the timeline and the API never need it; only Live view (RTSP) uses it. `POST /api/setup/cameras` takes `camera_user` and `camera_password` together or not at all (the wizard fills `rtspadmin` as the user); when given they are stored as that camera's own secret. Without one, Live shows "Add this camera's camera account in Settings to use Live view". Settings > Passwords and sign-in changes it. `POST /api/setup/account` accepts only the TP-Link pair `{email, password}`; a camera pair there is refused (400). The TP-Link account is required for Verify: it is the one account shared by all cameras, and Verify refuses uncounted ("Save your TP-Link account first") when it is missing.
- The account email is a non-secret setting in `<data dir>/settings.json` (`{"account_email": ...}`, written atomically). `credential_store` in the same file selects where the per-camera secrets live:
  - `keyring` (default): the OS keyring, service `kinora`, username = the key above. `backend_status()` says whether a backend works; with none, nothing is stored and the wizard offers `file`.
  - `file`: `<data dir>/secrets.json`, created with mode 0600 (O_EXCL, atomic replace keeps 0600). It is refused, with the `chmod 600` hint and no value read, if group or other users can read it (POSIX only; on Windows the folder ACL is the protection).
  - `env`: read-only. Per-camera store reads are skipped and writes are refused with a clear error; no camera or TP-Link secret is found this way (only the developer switch reads the environment).
- Store keys always start with `camera:` or `cloud:`. Other items under the same keyring service are never read or written.
- Passwords never appear in logs, exception text or `secret_sources` output (the wizard shows only `wizard`, `dev_override` or `missing`). Cache: after every write or delete of a secret the cached global camera secret and cloud password are dropped, so a corrected password is used on the next login.
- ffmpeg: found through `KINORA_FFMPEG` (full path to the binary) or `PATH`. Startup logs a warning if it is missing (the server still starts). With `KINORA_FFMPEG` set, its folder is put first on `PATH` at startup so pytapo finds `ffmpeg` and `ffprobe` beside it.
- pytapo's converter (P2P downloads and clips) needs `ffprobe` and a literal `ffmpeg` on `PATH`. Our own code no longer uses ffprobe. A missing tool is reported before any login as "ffprobe not found on PATH" (or ffmpeg, or both), not as a camera failure.
- Per-camera login method is in `cameras.json` (`auth`). `auto` (the default for cameras added by the wizard) is the login pytapo makes by itself: `Tapo(ip, "admin", cloud_pw, cloudPassword=cloud_pw)`, the TP-Link password for user `admin`, on the TPAP transport and on the legacy transport alike. The camera account is not used for it. `admin_cloud` is the same call (kept for cameras set up before `auto`). `cam_cloud` = `Tapo(ip, user, pw, cloudPassword=cloud_pw)` for older setups: the only login that uses the camera account. Settings > Passwords and sign-in > "Use automatic sign-in" switches a camera back to `auto` (it must be verified again; nothing logs in). Never auto-try several methods: every failed login counts against the camera.

## Login gate (why the cameras no longer lock out)
- Cameras suspend logins for ~30 min after repeated failures ("Temporary Suspension").
- `kinora/camera/gate.py` guards pytapo's own login primitives. Budget: 180 s between logins, 4 per hour per camera, a 2nd failure blocks 1920 s, a 3rd disables the camera, error -40211 disables it and forgets the transport. State persists in `cache/meta/breaker.json`, keyed by the camera's optional `device_id` in cameras.json (else its `id`).
- Budget updates from several processes are serialised by `cache/meta/breaker.lock` (an OS file lock), so the server and `tools/probe.py` cannot double the budget. A probe still spends logins: do not run it while a lockout is being debugged.
- Failures in the last 30 min are kept in `recent_fails` (pruned on write). Two failures inside that window block the camera for 1920 s, whatever the user did in between, so a typo cycle (wrong, fix, wrong, fix) gets at most two attempts per 30 min. `credentials-changed` never clears `recent_fails`.
- Recovery after you fix a password: save the new password in Settings (the camera account for Live view, or the TP-Link account), or run `python -m kinora.camera.gate credentials-changed <cam id>` (documentation and logs only: the page never shows it). Saving through `POST /api/cameras/{id}/credentials` clears the block (`disabled`, `fails` and the Live refusal), keeps the stored transport, and keeps the login history, `recent_fails` and any block. After you change the auth method, `--reset-auth` (or `reset_auth`) forgets the stored transport too. Never edit `breaker.json` by hand. Saving the TP-Link password (Accounts, or Settings) clears `disabled` and `fails` only, for the cameras that sign in with it (`auto`, `admin_cloud`): `gate.tplink_changed`. The blocks (`blocked_until`), `recent_fails` (so a second failure in 30 min still blocks 1920 s), the Live refusal and cam_cloud cameras are kept. A cam_cloud refusal is the camera account password: save it in Settings, or use "Use automatic sign-in".
- Adding a `device_id` to a camera that already had gate state: the state under the camera id moves to the device_id key on the next gate read (or merged with it, keeping the strictest values), so a block or a disabled camera stays so. The `device_id` must be a non-empty string, or cameras.json is refused at load.
- `GET /api/status` shows the state and never contacts a camera. Check it before any camera request.

## Setup API (first run and settings)
- Routes are under `/api/setup/*` and `/api/cameras/{id}` (full table in `docs/codemap/backend.md`). `GET /api/setup/state` and `POST /api/setup/reach` never log in; `POST /api/setup/verify` is the only route that can log in, and only one camera is verified at a time (a second request gets 409).
- A camera is added switched off and not verified. Only a successful Verify switches it on (`enabled` and `verified` are written together, after the login); a failed Verify, or a crash during it, leaves it switched off and verifiable again. A switched-off or unverified camera never logs in and never opens its video, so Live and the timeline refuse it before any camera contact. Verify refuses only a camera that is verified and switched on, answers `waiting` (no attempt) while the gate spaces logins, and never retries.
- **Model and presets.** The model is read from the device at the first successful Verify of a camera with no model recorded: the exact token C100, C200 or C210 (so `C1000` is not C100) sets its preset flags, in the same write as enabled and verified. C100 (the baby-monitor preset: p2p and stream_playback on, thumbs off, win 30, fast_forward on) also shows "Baby-monitor mode applied". C200 and C210 set ptz and fast_forward. An unknown model gets the C200 flags with p2p and stream_playback off and `model_note` "Unknown model: using standard settings". A flag the camera already has is never overwritten, and a re-Verify never applies presets again. Manual correction stays in Settings > Advanced: `PATCH /api/cameras/{id}` with `model` only records the model; with `"apply_preset": true` the flags are reset to that model's preset (`other` uses the C200 flags). Auth, enabled and verified are not changed and nothing logs in. The `model_mismatch` warning clears once `model` equals the model the camera reports. Changing p2p, stream_playback or fast_forward stops that camera's play and live; it is refused (409) while an export of the camera runs. Cancel or wait for the export first.
- Changing a camera's IP or auth sets it to not verified and disabled: the gate budget stays with the device, and Verify must run again. A TPAP login refused at `pake_register` (any code but -40401) on a camera whose stored transport is `tpap` forgets that transport and disables the camera ("The camera changed how it signs in"): save the TP-Link password again, then Verify. Removing a camera keeps its gate state (tombstone); adding it back at the same IP reuses the budget.
- State-changing requests need an `Origin` of `http://127.0.0.1:<port>` or `http://localhost:<port>` and `Content-Type: application/json`; anything else gets 403 or 415. Scripts that call the API must send both.
- Secrets are only written, never returned: the state shows the source of each secret (`wizard`, `dev_override`, `missing`). Each camera also shows `camera_user` (the user name of its own camera account, or null), `has_camera_account` and `live_refused` (Live was refused by the camera: the account password was not accepted). `account.email` is the saved TP-Link email (non-secret, or null). `prerequisites.credential_store.ok` is false, with a plain `reason`, when a saved password cannot be read; the cameras then show `missing` until it can.

## First run (fresh user)
The owner's watch-list for the first real use of the wizard on a new data folder. Visual checks (the player, the live picture, the camera names on screen) are the owner's: nothing here asks anyone to view a frame.
- The repo root must not contain `cameras.json`: move or rename it first. In the dev layout the repo root is the data folder, so a `cameras.json` there is read as the camera table.
- Only one server runs (see "Starting the server"). A second one exits; do not start it from another checkout to "try" the wizard.
- The new data folder starts with empty gate state, which is not a clean slate for the cameras: the last real login to each camera must be more than 30 min ago. Check `GET /api/status` first (every camera `connected:false`, `blocked_for_s 0`, `logins_last_hour 0`) before any camera request.
- Start the server without `KINORA_DEV_SECRETS`: then no environment variable or old Keychain item can be used in place of the wizard's passwords.
- Settings must show both secrets as saved by the wizard (`wizard`, not `dev_override`) for each camera and the TP-Link account.
- The Keychain prompt: approve it with Always Allow. A denied or locked prompt makes Verify refuse the camera with a message; it is not a login failure and does not count toward the lockout.
- Check the typed IP address and the three port ticks (443, 554, 8800) before pressing Verify.
- Kitchen first. Press Verify once and do not reload the page or stop the server while it spins. Then `GET /api/status` shows `logins_last_hour 1` for that camera only.
- After a refused login, correct the field before retrying. A second failure within 30 min blocks that camera for 32 min. With a Tapo-account camera, re-enter the TP-Link password before the next camera.
- Wait for success before starting the next camera.
- The first Live view is the first test of the camera-account password. A 401 from the camera disables Live for that camera until its credentials are saved again.
- Note any model-mismatch or different-device warning on the page. It is a warning: nothing is changed automatically.

## Starting the server
Installed: `kinora` (opens a browser tab; `--no-browser`, `--port N`, `--home PATH`; `kinora doctor` checks Python, data folder, ffmpeg/ffprobe, keyring and port without contacting a camera; `KINORA_NO_BROWSER=1` also skips the tab). From a checkout: `.venv/bin/python server.py` (a shim for `kinora/server.py`). Then http://localhost:8080 (localhost only; the server checks Host and Sec-Fetch-Site).

Only one server runs per machine. A second start (even from another checkout or with another `KINORA_HOME`) exits with "another Kinora server is already running on this machine" and the URL of the running one (the running server writes its port into `server.lock`). The lock is a file `server.lock` in the user cache dir, held until the server exits, so a crash never leaves it stuck. `KINORA_NO_INSTANCE_LOCK=1` disables it; that is for tests only.

First use after any change to login code:
1. Close the phone app and other clients. `pgrep -x ffmpeg` must print nothing.
2. Wait at least 30 min after any earlier failed attempt (especially Living Room).
3. `/api/status`: every camera `connected:false`, `blocked_for_s 0`, `logins_last_hour 0`.
4. Make the remembered camera Kitchen (`c201`). Do one request, then check `/api/status` again (`connected:true`, `logins_last_hour:1`, `transport` set).
5. Wait 5 min before Living Room (`c200`), then Baby Room (`c199`).
6. Any non-zero `blocked_for_s`: stop. Do not restart the server and do not run `tools/probe.py`.
Each restart costs one login per camera on first use. Opening the UI right after a restart logs in to the selected camera.

## Stream slots
A camera serves about two video streams, shared with the phone app.  Thumbnails run beside Live (cameras set `thumbs_beside_live:false` to go back to refusing them while Live is open; untested on real cameras). Clip downloads, exports, HLS playback and Live all need a slot, owned by `kinora.camera.slots.slots`:
a clip is refused while playback is open or starting; an idle Live relay (> 8 s) is stopped for a clip; playback waits up to 25 s for a clip, then stops Live.
Always close a stream you opened (`do stop` or UDT shutdown). Closing the tab stops playback; the server also stops it after 45 s idle or when the page is more than 120 s behind.

## Live view
`kinora/services/live.py` relays RTSP to HLS with ffmpeg (copy video, AAC audio) using the camera account, so it spends no API login budget.
The RTSP URL (with the password) is no longer on ffmpeg's command line: it is read from a private 0600 ffconcat temp file that is deleted ~6 s after start. If the camera rejects the camera-account password (`401 Unauthorized` on ffmpeg's stderr, case-insensitive; a bare `401` or `Unauthorized` does not count), the relay is stopped and Live is disabled until you fix the password and run `credentials-changed`; this survives restarts and shows as HTTP 503 with the reason. ffmpeg's stderr is never logged. Tested offline (`tests/test_live_argv.py`) and live on Kitchen on 2026-11-22 (playlist 200 in the first request, H.264 1920x1080 + AAC segments per ffprobe, no URL in ffmpeg's argv, temp file gone, no login spent). Living Room and Baby Room Live are not yet re-tested (ffmpeg input is `-f concat` with `option rtsp_transport tcp`); if Live fails there, `git revert` the live.py change.
The camera password was shown in earlier `pgrep -fl` output in this project: rotate it if that matters to you.

## Export
`POST /api/export {cam,start,end,mode}` (`video`, `audio_wav` = 16 kHz mono for ASR, `audio_m4a`), poll `GET /api/export/{id}`. Files go to `exports/` with a `.json` sidecar that maps output offsets to wall-clock times. Max 2 h per export, one at a time.
Baby Room exports run at 1x realtime through the P2P path.

## Pan/tilt
`POST /api/ptz {cam, dir}` uses `moveMotor(x, y)` in relative degrees (`ptz_step_deg`, default 10; `ptz_invert` exists). `-64304` is the end of travel, not an error. Never use `moveMotorStep`.

## Native thumbnails (C100 experiment)
Cameras with `p2p: true` and `native_thumbs: true` (the C100 preset sets it) answer `/api/thumb` by asking the camera for the thumbnail the Tapo app shows, over one short P2P session under the clip slot (`p2p_media.fetch_thumbnail`; the request shape is inferred from a decompile, so it may be wrong). Read the result in `server.log` after opening Baby Room: `[thumb <cam> native] first reply: {...}` is the camera's raw first answer (400 chars, no secrets); `[thumb <cam> native] unsupported: <reason>` means the camera refused or sent no image, after which every thumbnail request for that camera answers 404 until the server restarts (no more P2P sessions); `[thumb <cam> native <ts>] failed: ...` is a transient failure (502, not remembered). No log line plus images in the list means it works. To switch off, set `native_thumbs` to false in cameras.json.

**Native thumbnails, strategy 2 (snapshot).** The camera setting `native_thumbs_mode` (cameras.json, per camera, not in the C100 preset and not shown on the page) is `"image"` (default: the request above) or `"snapshot"`: pytapo's `getRecordingSnapshot` request (`download`, `media_type` 2, only a `start_time`) sent over the same P2P session (`p2p_media.fetch_snapshot`). In `"image"` mode, once the image request is remembered unsupported (per process), later requests use the snapshot request automatically; in `"snapshot"` mode the image request is never sent. To try it directly, set `"native_thumbs_mode": "snapshot"` on the Baby Room record (server restart or PATCH-free hand edit with the server stopped) and open Baby Room. Log lines in `server.log`, per camera and mode: `[thumb <cam> snapshot] first reply: {...}` (raw first reply, once per process), `[thumb <cam> snapshot] unsupported: <reason>` (error code, or `no reply (silence)`: remembered, 404 until restart), `[thumb <cam> snapshot <ts>] no image: ...` (camera acknowledged but has no image for that recording, typical for timed recordings; 404, not remembered), `[thumb <cam> snapshot <ts>] failed: ...` (502, not remembered). No line plus images in the list means it works. Detection-triggered recordings only are expected to have a snapshot.

## Privacy
These are private indoor cameras. Never view frames, thumbnails or clips and never open the player in a browser pane. Verify with API status codes, ffprobe metadata, logs and text, and ask the user to check visuals.

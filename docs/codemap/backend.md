# Backend

Python 3 + aiohttp. Always a loopback socket on 127.0.0.1:`config.PORT`; with sharing on (Settings > Other devices, `HOME/devices.json`) a second socket on the computer's LAN address (`devices_api.listen`/`set_sharing`). With `KINORA_HOST`/`--host` or `KINORA_ALLOW`/`--allow` the socket is on `config.HOST` (0.0.0.0 when devices are given on the command line), plus 127.0.0.1 unless HOST is 0.0.0.0 or 127.0.0.1, and sharing is read-only. `config.ALLOW` = command-line networks; `devices.is_allowed` = those or a stored device; `local_only` in server.py refuses other peers (403 with the waiting-list text, `devices.note_denied`), other Host names, and setup/camera-settings routes from non-loopback peers; tests/test_allow.py, tests/test_devices.py), port env `KINORA_PORT`, default 8080. pytapo 3.4.34 (pinned) does the camera calls.
Dependencies go inward: `kinora/server.py` -> `kinora/services/*` -> `kinora/camera/*` -> `kinora/{config,errors,creds,health}`.

Middleware order: `local_only`, `camera_errors`. `_serve` (server.py, used by `main`): `AppRunner`, `devices_api.listen`, SIGINT/SIGTERM stop the sockets through `runner.cleanup()` (cleanup contexts run); EADDRINUSE on loopback is the "Port N is already in use" exit. Startup tasks: prune, live reaper, health loop, play reaper. Cleanup stops play and live. `__main__` (top of server.py, before the other kinora imports) calls `instance.startup()` first (exit 1 with a message if another server holds it). `make_app(background=False)` builds the same app without the startup tasks (tests use it); `app = make_app()` is the runtime app.

## Invariants
- **Login gate** (`gate.py`): `MIN_LOGIN_GAP` 180 s, `MAX_LOGINS_PER_HOUR` 4, 2nd failure blocks 1920 s, 3rd or `-40211` disables the camera, "Invalid authentication" with no saved transport disables it (text: `gate.INVALID_TEXT`, user-facing, no CLI). A TPAP error from `pake_register` (any code but -40401) on a camera whose stored transport is `tpap` forgets the transport and disables it (`_tpap_conflict`, text `RELOGIN_TEXT`). A nested (pytapo-internal) login is counted but never records success or failure. `recent_fails` (persisted failure times, pruned to `FAIL_WINDOW` 1800 s on write): two entries in the window enforce `blocked_until = max(blocked_until, now + 1920)` regardless of `fails`; a state file without the key loads fine.
- **Gate locks**: every reload -> check -> save runs under `_state_lock` (threads) and an OS lock on `breaker.lock` (flock / msvcrt), released on exceptions. The clock is read inside the lock. `_save` writes a temp file then `os.replace`.
- **Gate identity**: state key is `gate_key(cam)` = `device_id` or else `id`; an IP change keeps the budget and swapped IPs do not swap state. `reload_cameras` mutates `CAMS`/`CAM_BY_IP` in place.
- **TP-Link saved** (`gate.tplink_changed`, called by `POST /api/setup/account` for auto and admin_cloud cameras): clears `disabled` and `fails` only.
- **Credentials changed**: `credentials_changed` clears `disabled`, `fails` and `live_disabled`, keeps `logins`, `blocked_until`, `recent_fails` and (unless `--reset-auth`) `transport`. Only reachable via the CLI (no HTTP route). Messages point at the CLI, never at breaker.json.
- **Runtime registry** (`kinora/cameras.py`): the server starts with zero cameras (`config.CAMS` empty is fine; `/api/cameras` returns `[]`). Lock order, always in this order: `_cfg_lock` (asyncio, one write at a time), then per-camera login locks (`session.login_lock`, taken in a worker thread, in id order when several are needed), then the gate lock only inside gate calls (never held across an operation; `gate._gate_lock` is not re-entrant). No gate call is made from `cameras.py`.
- **Quiesce**: an update that changes `ip` or `auth`, an update that switches a camera off (`enabled` true to false), and every remove, first stops play (`p2p_play.stop`) and live (`live.stop`) for the camera; an update that changes `p2p`, `stream_playback` or `fast_forward` (`PLAYBACK_KEYS`) stops play and live too, keeps the session (no login), and refuses while an export of it runs; an ip, auth or remove also refuses (`Refused`) while an export of it is queued or running, and a remove refuses while a clip or export holds the camera (`slots.busy`). Then the login lock is taken, the cached client is dropped, ip, auth and remove also clear health state (`health.forget`, which also drops checks already running), and only then cameras.json is written (in a worker thread, under `_cfg_lock`) and the table entry swapped. Name and flags changes do not quiesce. `device_id` cannot change; `id` is immutable.
- **Add**: creates the per-camera entries (`session.register_camera`, `slots.register_camera`) before publishing to `CAMS`/`CAM_BY_IP`; a new camera gets a random UUID `device_id` (or the one of a removed camera at the same IP) and `enabled: false` unless the caller passes otherwise. Failure before publish rolls the entries back.
- **Tombstones**: remove stores `{id, device_id, ip, removed_at}` in `TOMBSTONES` and cameras.json. A removed id is never reused (`add` refuses it). A camera added at a tombstoned IP reuses its `device_id` (a legacy camera without one keeps its id as the gate key).
- **cameras.json writes**: temp file in the data dir, fsync, `os.replace`; the previous file is kept as `cameras.json.bak`; the file is always `{"version":1,"cameras":[...],"tombstones":[...]}`. A crash before the replace leaves the old file intact. Writes are of the in-memory table: a hand edit made while the server runs is overwritten by the next registry write.
- **Dynamic tables**: `session._login_locks/_api_locks/_ctl_locks` and `Slots._locks/_wanted` are created by `register_camera` and removed by `unregister_camera`. `health.loop` checks the live dict each round; `health.check` drops a result whose camera was forgotten meanwhile. `live.reaper` and `live.stop_all` stop the relay of a camera that is no longer in the table instead of raising KeyError.
- **Corrupt breaker file**: the fail-closed table (`gate._load_state`) also covers the cameras being decided on (`_reload([cam])`), so a camera added at runtime is blocked too.
- **Per-camera credentials** (`creds.py`): `camera:<device_id or id>` and `cloud:<email lowercased>` in the store named by `credential_store` (`settings.json`, default `keyring`; `secrets.json` 0600 for `file`; `env` read-only). Every store key must start with `camera:` or `cloud:` (`_check_key`), so other items under service `kinora` are never read or written. Product path: `get_camera_credentials` uses only the camera's own secret and raises `RuntimeError` ("this camera has no camera account password stored") when there is none; `get_cloud_password_for` uses only the wizard secret of the saved email and raises "Save your TP-Link account first". `KINORA_DEV_SECRETS=1` (env, read by `dev_secrets()`; `announce_dev_secrets()` logs one line at startup) adds the legacy chain: env, `.env`, the macOS `security` CLI and the global keyring items; the cloud item is looked up only with the saved email as its account, never bare, and nothing is cached per account. In `keyring` mode a read that fails (denied prompt, locked keychain) raises `RuntimeError` and the caller refuses: it never reads as "no secret". Every write or delete calls `_invalidate` (clears the `get_credentials` cache and `_cloud`). `camera_state` does one store read per camera and returns `secret_sources` (`wizard`/`dev_override`/`missing`), `camera_user` (from the record, never the password) and `has_camera_account`; `secret_sources` is its `secret_sources` part.
- **Setup state** (`services/setup.py`): a store that cannot be read is reported once in `prerequisites.credential_store` (`ok` false, plain `reason`); the cameras show `missing`. Each camera has `live_refused` (the gate's `live_disabled` as a bool, no new logic). `account.email` is the saved TP-Link email.
- **Device identity**: `device_id` (non-empty string, validated in `config.load_cameras`) keys gate state, normalised by `gate_key`. `_reload` adopts or merges id-keyed state into the device_id key under the lock and saves.
- **KLAP**: `patch.install()` replaces pytapo's `Klap.authenticate` with a stub that raises `GateRefused`; `session.build` always passes `isKLAP=False` and only `pytapo`/`tpap` transports.
- **pytapo tools**: `binaries.require_pytapo_tools()` (ffprobe and ffmpeg on PATH) runs before any pytapo download or P2P fetch.
- **RTSP auth**: a `401 Unauthorized` (case-insensitive) in ffmpeg stderr sets a persisted `live_disabled` (until credentials-changed); `live_file` refuses with 503 before spawning ffmpeg. Stderr is drained, never logged or stored.
- `patch.install()` must run before any client is built (importing `session` does it). It refuses hosts not in `cameras.json`.
- `slots.Busy` is not a `CameraError`: `kinora/server.py` maps it to 503 itself. `p2p_media.Busy` is a different class. `play_start` maps `PlayError.kind`: busy 503, superseded 409, toomany 429, else 502.
- `session.api` never retries; on a session error it drops the client and raises `CameraError`. `as_http` turns gate-marked errors into `Unavailable`.
- **Slots**: clips, exports and live are refused while play is active. Idle live (> 8 s) is stopped for a clip. `play.start` waits `LOCK_WAIT_S` 25 s for the lock and releases it only in `_teardown`. Exports have no slot of their own (module lock: one at a time).
- **Media**: `STILL_RECORDING_S` 90 (the newest recording is not served), `WINDOW_FAIL_TTL` 300; two failures on windows older than 300 s pause media for `MEDIA_BLOCK_S` 1800.
- **Devices**: a remote peer is allowed when `devices.is_allowed` (config.ALLOW or a stored device IP; IPv4-mapped normalised; by IP address only) and sharing is on (`devices.sharing_on`); it may then call only `REMOTE_ROUTES` (server.py), and `LOCAL_ONLY_ROUTES` is the rest (tests/test_allow.py checks every route is in one of them). A peer whose address equals the connection's own local address (`_socket_ip`) is the owner (local). Origin from a remote peer must equal its own `http://<Host>`. Sharing off closes the open connections on the network socket (`devices_api._stop_lan`). A refused peer is recorded by address and time only (`note_denied`), never its request. Sharing state is only in `devices.json`; the live socket is `app[LISTEN]['lan_site']` (a dict, because aiohttp rejects app state changes after start).
- **Local only**: Host must be `127.0.0.1:PORT` or `localhost:PORT` (`config.allowed_hosts(config.PORT)`); `Sec-Fetch-Site` must be `same-origin` or `none`.
- **Origin rule** (`local_only`): POST, PUT, PATCH and DELETE need an `Origin` equal to `http://127.0.0.1:PORT` or `http://localhost:PORT`, else 403 (a missing Origin is not a fallback). They also need `Content-Type: application/json`, else 415; the one body-less route, `POST /api/export/{id}/cancel`, is exempt from the content type only. No error echoes a request body. GET is unchanged.
- **Login permission** (`session.client`): a camera logs in only when `enabled` and `verified` are both true. The check runs before the cached client is looked at, and again under the camera's login lock against the table entry (`_current`: a change of ip, auth or device_id while the request waited raises `Unavailable`, a retry). `VERIFYING` (set by `setup.verify`) is the only exception, for that camera while its Verify runs. Routes refuse first with 400 and no login (`session.check_usable`): recordings and events (also from cache), clip, thumb, ptz, play start, export, and `live_route` (no RTSP, so the camera password is never sent for a switched-off or unverified camera). Credentials are resolved before the gate: a credential error is a `BadInput`, never a counted failure.
- **Setup verify** (`setup.verify`): one camera at a time (module `_verify_lock`, a second request gets 409 at once). Refused (409) only when the camera is verified and switched on; an unverified camera is verified whether or not `enabled` is set. A gate wait (`gate.snapshot().wait_s`) answers `waiting` with no attempt. Missing secrets fail before any login. A camera that is still `enabled` (older files) is switched off first, so nothing enabled is persisted before a login. Then `session.client` makes the single login, then one `getBasicInfo` through `session.api`; any failure switches the camera off and drops its session, and leaves the gate as it is (no retry). Only on success is `enabled:true, verified:true` persisted, with `model_seen`, `fw_seen`; `mac` is stored at the first verify, and a later different MAC sets `mac_mismatch` and never changes the gate key. A crash leaves the camera switched off and not verified.
- **Setup camera records**: added with `enabled:false`, `verified:false`, and no model. The first successful Verify with a device-reported model sets `model` (the exact token C100, C200 or C210, else the raw string with `model_note`: "Unknown model: using standard settings") and the preset flags in the same `cameras.update` as `enabled`/`verified`; a flag the camera already has is never overwritten, and a re-Verify never applies presets. Browser objects are `setup.public(cam)`: id, name, ip, auth, model, model_note, device_id, enabled, verified, model_seen, fw_seen and `flags`. `mac` and the secrets stay server-side. `apply_preset` (PATCH, manual) sets the preset flags through `cameras.DROP` for those the preset does not name. `model_mismatch` in state is recomputed from `model` and `model_seen` on every read.
- **Caches**: clips 300 MB, thumbs 120 MB; play session dirs older than 3600 s are removed.
- **Health**: ports 443, 554, 8800; every 10 s; a camera leaves "ready" only after 2 misses. `health.forget(cid)` clears a camera's state.
- **Status**: `/api/status` takes the gate file lock (`gate._gate_lock`) as well as the thread lock, because `_reload` may save; a lock file that cannot be opened is reported as the in-memory state instead of an error.
- **P2P**: `day_list` returns earlier days first and the start day LAST (the camera plays from the last day listed); `prepare_session` re-lists on every start, then `getUserID`, then `request_p2p` (non-empty `stun_url`). `punch` gives up after 8 s, `UdtStream.connect` after 10 s; UDT payload 1376, MSS 1420.
- **Play** (`play.py`): `SETUP_TIMEOUT_S` 15, `STALL_S` 20, `IDLE_S` 45, `LAG_S` 120, `LAG_QUIET_S` 15. Two clocks: `last_get` (any request, playlist included) drives `IDLE_S` (page gone); `last_seg` (only `seg_*.ts` requests, set in `file_for`) drives the lag rule, which fires when the camera is `LAG_S` ahead AND no segment was requested for `LAG_QUIET_S`. A page that keeps fetching segments (a 16x session outrunning real time) is never stopped for lag; a paused hls.js page that only polls the EVENT playlist is stopped by the lag rule. A fast-forward session that keeps fetching is bounded by hls.js's buffer cap and `IDLE_S`, `KEEP_ENDED_S` 300, `MAX_RUN_S` 14400, `MIN_SETUP_GAP_S` 2, `MAX_STARTS_PER_MIN` 10. Video only (`-map 0:v -c:v copy`, 2 s HLS EVENT playlist); direct cameras (port 8800) get no second `do play` step, P2P cameras repeat the scale in `send_play`. `scale` is validated in `server.require_stream`, not in `play.py`.
- **Live** (`live.py`): `-rtsp_transport tcp`, AAC 64k, `IDLE_S` 45, a relay that dies within 30 s gives 502 and a 300 s block. ffmpeg stderr goes to a pipe drained by `_watch_stderr` (tail of 64 bytes kept); an auth match terminates the relay and calls `gate.note_rtsp_auth_failure`. ffmpeg input is `-f concat` over a private temp ffconcat file (`_write_secret_list`, deleted after `LIST_KEEP_S` 6 s) so the RTSP password is not in argv; `tests/test_live_argv.py` checks it.
- **Listings**: a day file saved more than 3600 s after the day ended is final; otherwise `TODAY_TTL`. A `CameraError` falls back to a stale copy.
- **Export**: pieces under 2 s dropped, cancel only checked between windows.
